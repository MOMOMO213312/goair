# رَنبوك التنفيذ — محدَّث بعد التنفيذ الفعلي على قاعدة البيانات الحية

بعد كتابة النسخة الأولى من هذا الملف، تم ربطي فعليًا بمشروع Supabase الحي
(`cvrjaprlnkutocvbnjhc`, مشروع GOAIR) عبر connector، ونفّذت الفحص والإصلاح
الأمني الحقيقي عليه مباشرة (مش سكريبتات نظرية). التفاصيل الكاملة في نص
المحادثة، وده ملخص تنفيذي:

## 🔴 الاكتشاف الأخطر: تجاوز مصادقة كامل عبر توكنات ثابتة قديمة — تم إغلاقه

كل صف في `transport_operators`, `travel_agencies`, `airline_partners`,
`ground_handling_partners`, `rental_partners`, `staff_access` كان عنده
`access_token` حقيقي وفعّال، ودالة `resolve_portal_entity` (وهي اللي بتتحقق
من صحة التوكن ده) كانت لسه **قابلة للاستدعاء المباشر من أي حد معه الـ anon
key بس** — من غير أي تسجيل دخول، ومن غير المرور بالتطبيق أصلًا. لو حد كان
عنده/خمّن/سرّب واحد من التوكنات دي (كانت مستخدمة قديمًا في روابط دخول قابلة
للمشاركة)، كان يقدر يدخل كأدمن/أوبريتور/شريك كامل الصلاحيات.

تأكدت بمراجعة الكود إن الفرونت إند بالكامل بقى يعتمد على Supabase Auth فقط
(صفر استخدام فعلي للتوكن القديم في أي مسار دخول)، فقفل المسار ده كان آمن
100% وظيفيًا. **تم تنفيذه فعليًا:**
- تدوير كل التوكنات القديمة لقيم عشوائية جديدة غير معروفة لحد (بيبطل أي
  توكن قديم مسرّب فورًا).
- إلغاء صلاحية التنفيذ المباشر (`REVOKE ... FROM PUBLIC` — لاحظ إن `PUBLIC`
  ضرورية مش بس `anon`/`authenticated`، لأن بوستجريس بيدي صلاحية `EXECUTE`
  لـ`PUBLIC` تلقائيًا وقت إنشاء أي دالة) عن `resolve_portal_entity`,
  `is_valid_operator_token`, `is_valid_staff_token`.
- تم اختبار الإصلاح فعليًا (`set local role anon`) قبل وبعد: قبل التعديل
  الاستدعاء المباشر كان بينفذ عادي (خطر مؤكد)، وبعده بيرجع
  `permission denied`، مع التأكد إن الاستخدام الشرعي (الدوال التانية اللي
  بتستدعيها من جوه زي `admin_list_bookings`) لسه شغال 100%.

## لسه محتاج منك (الوحيد اللي معنديش صلاحية أو أداة أنفذه بيها)

1. **فعّل حماية كلمات السر المسربة**: Supabase Dashboard → Authentication →
   Policies/Auth Providers → Password Security → فعّل "Leaked password
   protection". دقيقتين، مفيش بديل عبر SQL أو الـ MCP tools المتاحة ليّا.
2. **راجع باقي الـ178 دالة تدريجيًا** بترتيب الأولوية الموجود في
   `02_security_definer_functions.sql` (فئة المال/الحجز أولًا — 26 دالة).
   بدأنا بعينة (فئة فحص الجلسات) ولقينا فيها أخطر ثغرة في المشروع كله،
   فالباقي يستاهل نفس مستوى الجدية، مش مجرد نظرة سريعة.
3. **طبّق الـpatch الخاص بربط TripRing** (`tripring-ecosystem-link.patch`)
   على الفرونت إند وادفعه بنفسك على GitHub — الكود اتصحّح بعد ما تأكدت من
   القاعدة إن اسم الباراميتر الحقيقي هو `p_external_booking_reference` مش
   `p_pnr` زي ما كان موثّق (غلط) في الـREADME.
4. **قبل الإطلاق التجاري**: بعد ما تراجع باقي الـ178 دالة، شغّل
   `get_advisors` تاني (أو اطلب مني) للتأكد إن العدد نزل لصفر أو قريب منه.
